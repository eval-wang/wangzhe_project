# 王者荣耀打野轨迹自动提取系统 · 项目总纲

## 一、项目背景与目标

### 1.1 出发点
你是一位王者荣耀打野玩家，希望通过复盘自己的录像，系统化地分析打野路线、刷野效率、决策质量。最初你用手工方式在 Excel 中记录时间点和位置符号（如 `b0`, `R2`, `L`），但这种方式耗时巨大且无法规模化。

### 1.2 核心目标
**将“游戏录像”自动转化为“结构化时空数据集”**
### 1.3 最终愿景
积累足够多的对局数据后，通过机器学习挖掘“不同段位的最优刷钱路线”，形成可复用的策略知识。

---

## 二、整体架构：两阶段划分

| 阶段 | 名称 | 核心任务 | 输出 |
|------|------|----------|------|
| **阶段一** | 数据提取流水线 | 从视频中自动提取带地理标签的轨迹数据 | `trajectory.csv` |
| **阶段二** | 智能分析与训练 | 基于积累的数据进行模式挖掘与策略优化 | 决策模型 / 策略报告 |

**当前聚焦阶段一**，阶段二待阶段一稳定运行后启动。

## 三、阶段一：三大子项目拆解

阶段一被拆解为 **三个完全解耦的子项目**，可独立开发、测试、替换。

### 子项目1：小地图识别（自动ROI定位）

**目标**：从任意分辨率的录屏画面中，自动框出小地图区域，无需人工填写坐标。

**核心逻辑**：多特征投票机制

| 特征 | 检测方法 | 权重 |
|------|----------|------|
| 黑边矩形框 | Canny边缘检测 + 轮廓查找，筛选宽高比≈1:1且位于画面右侧的矩形 | 高 |
| 战绩按钮锚点 | 模板匹配（三条横线图标），反推小地图左上角 | 高 |
| 颜色分布特征 | 统计右上区域的绿色（草丛）+ 黄色（野怪点）密度 | 中 |

**输入**：视频首帧全屏图像  
**输出**：`(x, y, w, h)` 小地图在原始画面中的位置  
**验收标准**：换5个不同分辨率的视频，框选误差 < 5像素；处理时间 < 500ms

---

### 子项目2：英雄头像匹配（核心难点）

**目标**：在小地图上，通过图像匹配独立识别出“指定英雄”的像素位置，每帧独立处理。

**核心逻辑**：形状过滤 → 颜色直方图+人物识别

**为什么不用“时空连续性”**：英雄死亡会消失、回城会瞬移、团战会被遮挡，因此每帧必须独立判断，不依赖上一帧位置。

**输入**：
- 小地图底图（已归一化为正方形）
- 英雄头像模板图

**输出**：`(px, py)` 像素坐标；未识别到则返回 `None`  
**验收标准**：英雄存活时识别率 > 95%；死亡时稳定输出 `None`；单帧处理 < 100ms

---

### 子项目3：英雄位置定位（最确定、最简单）

**目标**：将子项目2输出的像素坐标，映射到 20×20 网格地图上，输出语义化标签。

**核心逻辑**：纯数学映射 + 查表

| 步骤 | 操作 | 公式 |
|------|------|------|
| 归一化 | 像素坐标 → 0~1 | `x_norm = px / 底图宽度`，`y_norm = py / 底图高度` |
| 离散化 | 归一化坐标 → 网格行列 | `col = floor(x_norm × 20)`，`row = floor(y_norm × 20)`，边界钳制（等价于 `floor(px / 9.3)`，186px / 20 格） |
| 查表 | 行列 → 地图符号 | 读取 `小地图位置.md` 中 `(row, col)` 对应的符号 |

**输入**：子项目2输出的 `(px, py)` + 20×20网格表  
**输出**：`(row, col, symbol)`  
**验收标准**：坐标映射100%准确；蓝buff位置输出 `b0`（与表格定义一致）

## 四、关键技术路线决策

### 4.1 抽帧策略
选择 **先抽帧、再逐图处理**（路线B），而非直接处理视频流。

- 用 `ffmpeg` 每3秒抽一帧，跳过中间89帧的解码，节省80%+ CPU算力
- 内存占用极低，断点续传方便，适合你的荣耀MagicBook Pro 14

### 4.2 英雄识别方案
放弃原MVP方案的HSV像素颜色检测，改用 **图像匹配（模板匹配 + 颜色直方图比对）**。

- 英雄头像在全局游戏中颜色恒定，且每个英雄有专属头像
- 霍夫圆检测先过滤候选区域，再对候选点做直方图比对，速度快、误报低

### 4.3 地图坐标系
采用 **20×20 网格**（400个格子），每个格子赋予语义符号。

- 原点 `(0,0)` 在左上角，右下角 `(19,19)` 
- 命名规范：参照“D:\wangzhe_project\相关素材\地图\命名格式plus.md”
- 符号表已通过 `D:\wangzhe_project\王者视频解析\子项目3_数据定位\小地图位置.md` 完成标注

## 五、数据流总览

```
原始视频 (MP4)
    │
    ├── ffmpeg 每3秒抽帧 → frame_0001.jpg, frame_0002.jpg, ...
    │
    ▼
【子项目1】小地图识别（首帧执行一次）
    输入：frame_0001.jpg
    输出：roi.txt (x, y, w, h)
    │
    ▼
【子项目2】英雄头像匹配（每张图独立执行）
    输入：frame_NNNN.jpg + roi.txt + template.jpg
    输出：每张图对应的 (px, py) 或 None
    │
    ▼
【子项目3】英雄位置定位
    输入：(px, py) + 底图尺寸 + 小地图位置.md
    输出：(row, col, symbol)
    │
    ▼
最终输出：trajectory.csv
```

## 六、开发优先级

| 顺序 | 子项目 | 理由 |
|------|--------|------|
| 1 | 子项目3（位置定位） | 最确定、无算法风险，可先用已有MVP数据测试查表逻辑 |
| 2 | 子项目2（英雄头像匹配） | 核心难点，需要反复调参，优先攻克 |
| 3 | 子项目1（小地图识别） | 相对独立，可先用固定ROI占位，最后替换为自动化版本 |

---

## 七、接口约定（子项目间解耦的关键）

- **子项目1 → 子项目2**：传递 `(x, y, w, h)`，用文本文件或JSON存储
- **子项目2 → 子项目3**：传递 `(px, py)`，用CSV中间列存储
- **子项目3**：只依赖像素点 + 网格表，完全不感知前两个子项目的实现

每个子项目都可以独立测试、独立替换算法。
