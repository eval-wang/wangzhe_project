# 架构设计

> 本文档描述 pipeline 的整体架构、分层职责、数据流与关键设计决策。
> 阅读对象：准备理解或修改本项目的开发者。

## 1. 系统上下文

本 pipeline 是"王者荣耀打野轨迹自动提取系统"**阶段一（数据提取流水线）的调度层**。
三个子项目（小地图识别 / 英雄头像识别 / 数据定位）各自独立开发、独立验收，
本仓库不重新实现它们的算法，而是：

1. 以**只读方式**复用子项目的模型文件与推理代码；
2. 按统一的**产物目录规范**组织输入输出；
3. 提供**一键调度、断点续跑、并行加速、问题帧归档**等工程能力。

```
┌─────────────────────────────────────────────────────────────┐
│                      pipeline（本仓库）                       │
│  ┌───────────┐   ┌───────────┐   ┌───────────────────────┐  │
│  │ stage1    │ → │ stage2    │ → │ stage3                │  │
│  │ 抽帧裁切   │   │ 英雄检测   │   │ 网格+符号+填表+UN归档  │  │
│  └─────┬─────┘   └─────┬─────┘   └──────────┬────────────┘  │
└────────┼───────────────┼────────────────────┼───────────────┘
         │ 只读引用       │ 只读引用            │ 只读引用
         ▼               ▼                    ▼
  子项目1 roi_model   子项目2 hero_detect   子项目3 小地图位置.md
  + core 特征提取     + hero_model.pkl      相关素材 基础表格.xlsx
```

## 2. 分层结构

| 层 | 模块 | 职责 | 可替换性 |
|---|---|---|---|
| 调度层 | `pipeline.py` | 解析 document、定位视频、按序调用三阶段、汇总报告 | 可替换为任意工作流引擎 |
| 阶段层 | `stage1_extract.py` / `stage2_detect.py` / `stage3_locate_fill.py` | 各阶段的输入校验、产物组织、归档逻辑 | 阶段间仅通过文件契约耦合，可独立重跑、独立替换 |
| 依赖层 | 子项目1/2/3 的模型与代码（仓库外，只读） | 核心算法：ROI 回归、头像检测、符号映射 | 模型文件升级不影响本层接口 |

**依赖方向严格单向**：调度层 → 阶段层 → 依赖层。阶段层之间不互相 import，
只通过 `apply\documentN\subprojectN\` 下的文件产物通信。

## 4. 关键设计决策（ADR 摘要）

### ADR-1：阶段间用文件而非内存对象通信

- **决策**：stage1→2 传帧目录，stage2→3 传 CSV。
- **理由**：符合总纲"子项目完全解耦"原则；任一阶段可单独重跑；
  中间产物保留供复盘（用户明确要求"现阶段不成熟，需要用来复盘"）。
- **代价**：磁盘占用增加（每局约 250 张 jpg），可接受。

### ADR-2：只读引用子项目，不做任何修改

- **决策**：子项目1/2/3 的脚本与模型一律只读；需要不同的输出逻辑时，
  在 pipeline 内创建**规范化副本**（如 stage1_extract.py 之于 extract_minimaps.py）。
- **理由**：子项目仍处在独立迭代中，保持其可独立运行、可回退的状态；
  修改需求通过"修改建议"机制回流（见 CONTRIBUTING.md）。

### ADR-3：检测阶段多进程并行 + 断点续跑

- **决策**：stage2 用 `ProcessPoolExecutor`（默认 6 worker）并行检测；
  结果逐条追加落盘，重跑时按文件名跳过已检测帧。
- **理由**：单帧检测约 3.3s（CPU 密集），251 帧串行需 ~14 分钟；
  并行后 ~2 分钟。逐条落盘使中断成本为零。
- **注意**：Windows 下多进程为 spawn 模式，worker 函数必须模块级定义；
  每个 worker 独立加载模型（内存换吞吐）。

### ADR-4：网格换算用 floor 而非 round

- **决策**：`col = floor(px / 9.3)`，`row = floor(py / 9.3)`，边界钳制到 [0, 19]。
- **理由**：与子项目2/3 的既有实现保持一致（代码为准，文档已同步修正）。

### ADR-5：EM / UN 语义分离

- **决策**：`EM` = 检测失败（阶段2 职责，归档到 subproject2）；
  `UN` = 检测成功但 (row,col) 未标注（阶段3 职责，归档到 subproject3）。
- **理由**：两类问题的责任方和修复路径不同——EM 指向检测模型改进，
  UN 指向地图标注补全。分离归档让复盘时各归其位。

### ADR-6：document 维度组织产物

- **决策**：一局录像 = 一个 document（`apply\documentN\`），
  三个阶段产物置于其下 `subproject1~3\`；阶段文件夹由脚本自动创建。
- **理由**：路径即元数据——从产物路径即可反推对局与阶段，满足"可追踪、可复盘"。

### ADR-7：时间基准固定 40s，放弃自动校准

- **决策**：抽帧从视频 00:40 开始，与基础表格起点对齐；不做开局自动检测。
- **理由**：现阶段录像均从开局前手动起录，固定偏移简单可靠；
  自动校准列入路线图（见 ROADMAP.md）。

## 5. 错误处理与降级策略

| 故障点 | 行为 |
|---|---|
| 视频不存在 / 无法打开 | 阶段1 抛 `FileNotFoundError` / `RuntimeError`，流水线中止 |
| video_footage 下多个 mp4 | 抛 `RuntimeError`（一个 document 只对应一个视频） |
| 裁切尺寸异常（>3% 偏差） | 跳过该帧并记入 extraction_log.csv，不中断 |
| 单帧无法解码 | 阶段2 记 `unreadable` 状态，继续下一帧 |
| 检测中断（超时/手动停止） | 已检测帧不丢，重跑自动续 |
| (row,col) 查不到映射 | 记 UN 并归档，不视为错误 |
| 采样超出表格 17 列 | 丢弃（已确认的产品决策） |

## 6. 扩展点

- **新对局**：放入 `apply\documentN\video_footage\`，`--document documentN` 即可。
- **新英雄**：在子项目2 中标注训练新模型，替换 `hero_model.pkl`（本仓库零改动）。
- **新分辨率**：在子项目1 中补充标注重训 `roi_model.pkl`（本仓库零改动）。
- **新阶段**：按 `stageN_xxx.py` 模式新增，在 `pipeline.py` 的 `run()` 中串联，
  产物目录遵循同一命名规范。
